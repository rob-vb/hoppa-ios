## Destination

A set of validated visual prototypes (made with `/design`), an English domain model (`CONTEXT.md`), and a written spec for **Fitty**: a public iOS app for tracking strength-training workouts. The build phase (SwiftUI implementation, backend, App Store release) is a separate, later effort.

## Notes

- **Tracker**: local markdown. Issues live in `issues/`, one file per issue, numbered. A ticket is a child of this map via `parent: 1` in its frontmatter. Claim a ticket by filling `assignee:` before any work. A ticket is blocked while any id in `blocked-by:` has `status: open`. The frontier = open, unassigned, unblocked tickets. Close a ticket by setting `status: closed` and appending a `## Resolution` section.
- **Skills**: consult `CONTEXT.md` for vocabulary in every session. Prototype tickets use `/design` (with the frontend-design and dataviz skills where relevant) and the mattpocock prototype skill. Grilling tickets use grilling + domain-modeling.
- **Standing preferences**: all domain terms, UI copy, and project documents in English; conversation with the user follows their CLAUDE.md (Simplified Technical English, Dutch when they write Dutch). Dark theme first: big numbers, high contrast, thumb-friendly for gym use. The user strength-trains themself and is the first test user — put design choices to them as concrete options to react to. Visual first: no backend or persistence decisions on this map.
- **Charter decisions** (settled while charting, before any ticket):
  - Prototype scope: onboarding (Program entry), workout logging, plate display. Static artboards first, then one clickable HTML prototype for the logging flow.
  - Domain model: Program → Workout Days → Exercises; see `CONTEXT.md` for all terms and progression rules (Progressive Overload, Microloading, increments, equipment types, plate inventory defaults, kg + lbs).
  - Progression Mode sits on the Program (default: Progressive Overload); per-Exercise override allowed. No automatic deload.
  - Rest timer counts up, stopwatch-style, auto-starts after each set.
  - Onboarding: manual Program entry gets all the design energy; templates come later.
  - Working name: Fitty. Final name out of this map's scope.

## Decisions so far

- [Design language & visual direction](0002-design-language-and-visual-direction.md) — Direction A "Plate Rack" is the standard: `#0E0F10` floor, calibrated plate colours as the palette (colour only ever means weight), Anton + IBM Plex Sans, 2–3 px radii, signature = the loaded bar drawn to scale. The logging screen's bottom row is `−` · `LOG n REPS` · `+`, so reps above the Rep Range can be logged.
- [Workout session lifecycle](0003-workout-session-lifecycle.md) — free pick of the Workout Day (no rotation), explicit start, one Open Workout at a time. Every Exercise is Open, Completed, or Skipped; navigating past means "later", skipping means "not at all". Finish is gated on no Open Exercises, with a one-tap "skip the rest and finish". Discard exists behind a menu. Progression is per Exercise and needs all planned Sets, so "Done early" never progresses. Finish leads to a Workout Summary with confetti scaled to the count of progressed Exercises.
- [Progression edge cases](0004-progression-edge-cases.md) — Fitty applies the progression at Finish; no suggestion, no acceptance. Reps above the range progress once, never more. The user changes the weight on the Exercise card: raising sticks, lowering asks "Just today, or from now on?", and a One-off Weight never writes back. A long gap does nothing. **The Weight Unit moved from the Program to the Exercise**, so one Program mixes kg and lbs; the Plate Inventory decides the unit for the three plate-loaded Equipment Types, and the Microloading Increment is a Microplate the user owns (`100 lbs + 1.25 kg`).

- [Plate display design](0005-plate-display-design.md) — Barbell, Smith Machine and Plate-loaded Machine all draw the **same loaded bar**; only the Base Weight text differs. Stack/cable draw the pin with the Microplate on it, Dumbbell draws steel, Bodyweight draws the plate on the belt. Mixed units stack as two numbers with their own labels and never convert. The Plate Inventory is on/off per plate size, with no count of pairs. Unreachable weight: the big number stays the Working Weight, and a steel `≈ CLOSEST` line under the bar names the closest buildable load and the difference (tie rounds down). Progression never snaps to buildable weights.

- [Program onboarding flow prototype](0006-program-onboarding-flow-prototype.md) — Fitty starts **empty**. Three steps: name the Program (with Weight Unit, Progression Mode and Plate Rack shown as pre-answered, one tap from being changed), confirm the plate rack, then the Program sheet as the hub. Exercise entry is the **full sheet, Model B**: nine fields on one screen, chosen over a ~113-tap-cheaper fast list because Fitty targets a lifter who already knows their equipment. Only Sets and Rep Range carry over from the previous Exercise; everything else is picked by hand. The name field proposes known names but free text always wins, and a suggestion sets the name and nothing else. **14 taps per Exercise, 400 for a 4-day/22-exercise Program.**

- [Workout logging clickable prototype](0007-workout-logging-clickable-prototype.md) — Approved on the first pass. The weight edit is a keypad sheet with `−`/`+` at the Increment; raising closes at once, lowering asks *Just today, or from now on?*. A One-off Weight is marked by a steel `ONE-OFF · 72.5 KG STAYS` chip beside the unit and on every Set row. The artboard's `+2.5 NEXT` became a **rule chip**: steel `+2.5 KG IF ALL 12` while logging, green `→ 75 KG NEXT TIME` at completion — a statement, never an offer. The last Set completes the Exercise by itself; the bottom button then becomes `NEXT: <exercise>`, so moving on costs one tap and Fitty never jumps by itself. The exercise counter `3 / 5 ▾` is the navigation. The logic lives in a pure module (`Fitty`) built to lift into the real app.

- [Workout summary screen prototype](0009-workout-summary-screen.md) — The **count is the hero**, and there is no Accept and no Undo: Fitty applied the weight at Finish, so the green `72.5 → 75 KG · NEXT TIME` is a statement of fact. Confetti is **Ignition**: each Went-up row lands 190 ms after the one above it and throws a burst from its own plate chip, ~1.4 s in total, nothing at all when zero progressed. Particles are plate-shaped and take the **per-side Plate Breakdown of the new weight**, so colour still means weight (colouring by the Increment came out almost all red; density-scaled bursts covered the numbers at five Exercises). Every **stayed** Exercise states its condition — `ALL 3 SETS AT 12 → 75 KG` — which is what keeps the zero-progressed screen worth reading without scolding or consoling. Mixed units confirmed: per-Exercise lines never convert, total volume converts to the Program default.

- [Exercise name suggestions](0010-exercise-name-suggestions.md) — Two sources in one ranked list: the user's own names on top, a shipped **Exercise Catalogue** of ~150 names underneath, deduplicated. The own-names source is **derived live from every Exercise in every Program**, never stored, so a rename or a delete updates it at once and no cleanup screen exists. The **Name is a label, not an identity**: two Exercises sharing a name stay two Exercises with their own Working Weight, and a rename keeps the logged Sets. Matching starts at any word (`incline` finds both orders); on focus the field shows the six most recent own names and no catalogue entries; the catalogue is never browsable and never filtered by Weight Unit or Equipment Type. Catalogue order is curated and fixed, and equipment goes in front of a name only where the same movement exists on more than one Equipment Type — a mechanical rule, so `Bench Press` splits three ways while `Leg Press` stays bare.

- [Microplate accumulation](0011-microplate-accumulation.md) — The accumulation was a symptom of Fitty holding **two** models of Microloading; collapsing them removes the question. Microloading now raises the **Working Weight** like any other progression, and the prototype's microplate counter is deleted. Only the mixed-unit case keeps a second number: the **Microload**, a weight in the Plate Inventory's unit, which exists only where the Exercise's unit differs. Fitty stores a weight and never a count, and solves it from the biggest plate down, so `+1.25 kg` draws as one plate and there is nothing to roll up. A bar takes a **pair**, so a 0.25 microplate moves it 0.5; every other Equipment Type takes one plate, and none is blocked. **Against my recommendation, the Progression Mode decides which plates the solver may use** — Progressive Overload uses normal plates only, Microloading uses the Microplates too — because Progressive Overload is the common case and must never be told to hang a 0.5. Ticket 7's `61.25 kg` walkthrough therefore stands unchanged. New Exercise field **Stack Step**; the stack weight sheet gains `PIN` and `MICRO` steppers. The **palette becomes the user's real rack** (20 blue, 10 green, 5/2.5/1.25 in three greys, microplates 1 red · 0.75 blue · 0.5 green · 0.25 white; no 15 kg), which breaks ticket 2's rule: *colour only ever means weight* becomes **colour plus size means weight**, held up by **a plate is always filled, steel is never filled**.

- [Assemble the spec](0008-assemble-the-spec.md) — **[`SPEC.md`](../SPEC.md) exists: the destination artefact.** Eleven sections covering the product rules, the domain model as fields per entity, the lifecycle, progression, the Plate Breakdown, the three validated flows, the visual language, the prototype code and its known defects, the open items and a decision index. `CONTEXT.md` stays the only home of the glossary; the tickets stay the only home of the reasoning. Assembly surfaced one real conflict between two closed tickets and three palette details no ticket ever fixed; both were then settled, by [Confetti plate source](0012-confetti-plate-source.md) and [Plate Inventory shipped defaults](0013-plate-inventory-shipped-defaults.md).

- [Confetti plate source](0012-confetti-plate-source.md) — **the burst throws what the Plate Breakdown draws**, on every Equipment Type: the bar throws its per-side plates of the new weight, the stack throws its Microplates plus one steel slab per loaded pin block, the dumbbell throws steel, bodyweight throws the belt plate. [Microplate accumulation](0011-microplate-accumulation.md)'s "the plates that changed" is retired — it solved the stack and reached into the bar, where it became the rule [Workout summary screen prototype](0009-workout-summary-screen.md) had already tested and rejected. Sampling is **proportional by plate count** (one share per distinct size would make a plate louder as it got smaller; by mass would erase the microplate on a 61.25 kg load). **Steel particles are hollow**, per *steel is never filled* — a filled steel slab reads as a rack of 1.25s.
- [Plate Inventory shipped defaults](0013-plate-inventory-shipped-defaults.md) — 25 kg is **red `#C8322B`**, sharing red with the 1 kg microplate as blue and green already share. **Every Microplate ships OFF** in both units (kg 0.25/0.5/0.75/1, lbs 0.5/1/1.25/2.5), because most gyms own none; the Inventory footer then states only `Smallest jump on the bar: 2.5 kg` and earns its Microloading clause when a plate is switched on. This supersedes ticket 6's "both Microplates on". Choosing Microloading with an empty Microplate group **opens that group as a sheet in place** rather than disabling the Mode — Fitty states its condition where the user stands, it never makes them hunt for a reason. The shipped palette stays this one gym's iron rack, knowingly; a second bumper/IWF palette was raised and deferred to **User-set plate colours**.

- [Editing a Program over time](0014-editing-a-program-over-time.md) — The first question moved the ticket: **the model had no place to put the past.** A Set held the rep count only and read the weight live off the Exercise, which progression raises at every Finish, so every past Workout already showed the wrong number before any edit existed. **A Set now stores its own reps, weight, Weight Unit, Microload and One-off mark** — per Set, because the weight can rise part-way through an Exercise — and no later edit touches it. It stores **no Plate Breakdown**: that is a solve, not a fact, and storing the picture would make every Inventory edit a history migration. **Fitty stores the numbers and looks up the name**, falling back to a stored Name only after a delete, so a rename still fixes a typo everywhere. Three of the five data rules then fell out as consequences. **An edit at the rack is a Program edit** and sticks at once — the lifecycle already covers "fewer Sets today" (end early) and "lighter today" (One-off). Progression's test becomes **at least the planned Sets**, read as the Exercise stands at Finish, which kills the arithmetic surprises; raising planned Sets **reopens** a Completed Exercise. **Units never convert now covers the stored number**: changing a Weight Unit clears the Working Weight, Increment and Stack Step and re-asks them, and at Inventory scale the same rule hands over a one-screen **Re-weigh list** rather than ambushing the user at twelve future racks. Switching a Microplate off warns with a count and strands its Exercises into the empty state 0013 already drew. **A delete can no longer destroy history**, so its confirm is plain. Deleting a *past Workout* moved to [History and progression charts](0015-history-and-progression-charts.md). Against the ticket's own prediction, the user **declined a prototype ticket** for the screens: only the Re-weigh list, two dialogs and reorder handles lack precedent, so flow 5 is specified (`SPEC.md` §6.6) and not drawn.

- [History and progression charts](0015-history-and-progression-charts.md) — Flow 4 exists, on ten artboards whose every number is the output of Fitty's own rules run forward over sixteen weeks. **Two doors and no tab bar**: a HISTORY row at the foot of the day picker, and every Exercise card in the Program sheet. Three views ship — the per-Exercise chart, the Workout list, a week streak — and the overview and volume views were dropped on mixed units. The line is the **Working Weight in steel**, because a plate colour would claim to be a plate; green stays progression, so a green dot is a session that earned the step. **The ticket's own answer lost to the alternative it provoked**: reps as figures over the points collide at fifteen sessions and carry two meanings, so the reps became a **Set grid** under the line — three filled cells *is* the progression rule, stated without a word. New: a **dashed NEXT step**, because Fitty applies the weight at Finish and the hero would otherwise contradict the end of the line — solid is lifted, dashed is not. A One-off hangs off the line and never fills its grid column; a Skip draws nothing, since the x axis is real time; charts never join by Name. Mixed units plot the **Microload**, because the pin has not moved in fifteen weeks. The **streak states and never punishes** — one Workout makes a week, a missed week is a darker block and nothing else, and there is deliberately no best-ever number to fall short of. **Deleting a past Workout keeps the Working Weight**, and its red button settles a palette question: a plate colour is a plate **only inside a Plate Breakdown**. Running the rules that far also found a hole no screen had shown, now [Bounding the Microload](0016-bounding-the-microload.md).

- [Bounding the Microload](0016-bounding-the-microload.md) — **The pin moves.** This ticket's own premise was wrong and its own recommendation lost: it claimed a roll-up would need a forbidden conversion, but `SPEC.md` §4.2 already says Fitty *does* the mixed-unit arithmetic and only never **shows** it. The ban is on displaying a converted number, not on computing one, which reopened the option the ticket had ruled out. The recommended ceiling was wrong too — the sum of the switched-on Microplates gives whoever owns one size exactly **one** progression. The rule: a Microload that reaches one Stack Step adds that step to the Working Weight and keeps the remainder, **rounded up** to a buildable weight. Two invariants, both checked over 40 progressions in four gyms: the **Microload stays under one Stack Step**, and the **weight never goes down** — the round-up buys that for at most one Microplate. The screen explains nothing: `90 LBS + 4.5 KG → 100 LBS + 0.25 KG`, and a `PIN MOVED UP ONE STEP` line was drafted and rejected. Scope fell out with it: **a Microload exists only where there is a Stack Step**, so **Bodyweight joins the Inventory-unit group** (its added weight *is* a plate off the user's rack — a rule §2.6 had simply never applied there, which closed that hole without an answer), and a **Dumbbell in the other unit cannot microload** at all.

## Not yet specified

Nothing. The fog is cleared: every patch that was in it either became a ticket and was resolved, or was ruled out of scope below.

## Out of scope

- The build phase: SwiftUI implementation, persistence/backend, App Store release. This map ends at a validated spec.
- Writing out the ~150 names of the Exercise Catalogue. Content work for the build phase; [Exercise name suggestions](0010-exercise-name-suggestions.md) fixed the naming rule, the size and the order that govern it, and that is as far as a spec needs to go.
- **Template library** (5/3/1, PPL, …): how templates and manual entry meet. Onboarding was built empty-first on purpose ([Program onboarding flow prototype](0006-program-onboarding-flow-prototype.md)).
- **Equipment profiles shared across Exercises** ("Smith machine at my gym, 7 kg base"). Sharpened but not adopted: Base Weight is typed by hand on every Smith and plate-loaded Exercise with no default, so a profile is exactly what would replace that repetition.
- **Warm-up sets**: whether Fitty shows them and computes their plates.
- **Bodyweight rep-progression before added weight** (chin-ups without a belt).
- **Deload guidance after repeated failure.** [Progression edge cases](0004-progression-edge-cases.md) decided Fitty does nothing, and the reason stands: it has no data to pick the right deload.
- **Definitive app name.** The charter always put the final name outside this effort; it was listed as fog by mistake, and that is now corrected.

The six above were ruled out together while working the map's last open items. Each is a **new feature, not a hole** in the flows this map validated, so each is a later effort rather than a resumption of this one.

- **User-set plate colours.** The last patch of fog, ruled out rather than worked. The shipped palette is one gym's iron rack: 5, 2.5 and 1.25 in black, where a bumper or IWF set paints them white, red and chrome and 25 red — so most public users will see wrong colours, and it should ship before the app is public. It is still a **new feature, not a hole**: [Plate Inventory shipped defaults](0013-plate-inventory-shipped-defaults.md) shipped one honest palette knowingly, and [Microplate accumulation](0011-microplate-accumulation.md)'s rule *colour plus size means weight* survives any palette that replaces it, so nothing in the spec depends on which rack it is. A second palette needs the same care as the first and re-opens which colour means what — that is a design effort of its own, not the last step of this one.

- **Several Plate Inventories, one per gym.** Fitty holds one. [Editing a Program over time](0014-editing-a-program-over-time.md) made the cost of that explicit — changing the Inventory's unit clears and re-asks the weight on every plate-loaded Exercise in every Program — and then accepted it, because saved racks are a feature and not the missing half of a flow.

## Resolution

**The destination is reached.** [`SPEC.md`](../SPEC.md) is the artefact this map was for:
eleven sections, five flows, the domain model as fields per entity, the progression rules, the
Plate Breakdown, the visual language, the prototype code and a decision index back to every
ticket. [`CONTEXT.md`](../CONTEXT.md) holds the glossary and nothing else. Fifteen tickets, four
published prototypes and one design canvas per prototype ticket sit behind it, and the reasoning
stays in the tickets — the spec states what was decided, never why.

The way is clear. Nothing is left to decide before someone builds it, and the fog is empty:
every patch either became a ticket and was resolved, or is listed in **Out of scope** above with
its reason.

### What the map turned out to be for

Two things it did not set out to do, and both were worth more than a screen:

1. **It kept catching itself.** Ticket 8 found a conflict between two closed tickets; ticket 14
   found that the model had nowhere to put the past, so every finished Workout had been showing
   the wrong weight; ticket 15's charts found that nothing ever stopped a Microload — which
   ticket 16 then fixed, on a premise ticket 16 itself had got wrong. A map that only ever added
   decisions would have shipped all four.
2. **It built the rules as code and ran them.** The logging prototype's `Fitty` module and the
   history generator are the only things here that ever executed the progression rules, and the
   generator is the only one that ran them further than one Workout. That is what exposed §4.2's
   hole. Worth re-running against the real implementation.

### Where the build starts

`SPEC.md` §1.1 for the scope, §8 for what to lift from the prototypes and what they have wrong,
§10 for the eight features deliberately left out. **User-set plate colours** is the one out-of-scope
item with a deadline attached: it should ship before the app is public.
